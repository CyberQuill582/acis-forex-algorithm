## Findings

### F-E1 — The single-writer precondition fails SILENTLY when violated, and the spec's own writers of `rung_state` are out-of-band; for the provenance store the staleness is not "until this instance next writes" but potentially forever
- Severity: **high** · Likelihood: **medium** (nothing violates it today; the phase-12 runtime, the out-of-band harness, and the fold-parallel 16-core evolve design are all unbuilt)
- External referent — SQLite `sqlite3_total_changes` (https://sqlite.org/c3ref/total_changes.html): *"The sqlite3_total_changes(D) interface only reports the number of rows that changed due to SQL statement run against database connection D. Any changes by other database connections are ignored. To detect changes against a database file from other database connections use the PRAGMA data_version command or the SQLITE_FCNTL_DATA_VERSION file control."* — i.e. the mechanism the caches key on is, by its own documentation, blind to the exact case the precondition rules out.
- Spec referents: ACIS-11 header table — *"Consumes: … re-validation verdicts (phase-11 harness / Phronesis via §12)"*; ACIS-11 §11 — *"No MCP tool mutates provenance; verdicts arrive via the phase-11 harness in-process"*; master §12 — *"`acis_run_backtest(params)` / `acis_report(period)` — out-of-band analysis"*; master §10 — *"Three independent asyncio loops sharing read access to stores"*; TODO.md 16-core item — fold-parallel evolve on c7i.4xlarge. The locked ACIS-11 §11 supports "in-process" for verdicts, so the precondition is spec-consistent in words; but the harness that computes verdicts is the out-of-band backtest, and nothing in code or deploy enforces the process boundary.
- Why the ledger's own wording understates it: `KNOWN_GAPS.md` GAP-P12D-15 says a second writer *"would go unseen until that instance next writes"*. For `ProvenanceStore` the engine's fast loop **never writes** (`grep` for `apply_revalidation(`, `.demote(`, `prov.on_boundary` outside tests: only the store itself and tests; `PaperLoop.on_state` calls only `entry_allowed`). So an out-of-process `apply_revalidation("FAIL")` — the ACIS-11 §7 *"Instantly (same call): entries_frozen = True — AGON's entry_allowed() returns False from this moment"* — would never reach AGON's gate for the life of the process.
- Reproduction (`ext_audit_sqlite.py`, the exact `entry_allowed` logic on connection 1, a second connection writing the same file):
  ```
  other-conn UPDATE: total_changes delta 0 | data_version changed: True | row visible to conn1 SELECT: 1
  engine sees s2 allowed: True
  after other-conn freeze, engine cache says allowed: True | truth in file: False
  after the engine's own next write: False
  ```
  An uncached SELECT on the same connection sees the row; the cache does not. The freeze becomes visible only after connection 1 performs any write of its own.
- Minimal fix (either makes the precondition structural instead of promised; costs are from F-E2):
  1. **Enforce it:** `self._db.execute("PRAGMA locking_mode=EXCLUSIVE")` in both store constructors (before the first read/write). Per https://sqlite.org/pragma.html#pragma_locking_mode: *"The first time the database is read in EXCLUSIVE mode, a shared lock is obtained and held. The first time the database is written, an exclusive lock is obtained and held."* A second connection's write then raises `sqlite3.OperationalError: database is locked` (reproduced: `second writer under EXCLUSIVE -> database is locked`) — loud, never silent. Trade-off, per lockingv3: *"no other locks of any kind are allowed to coexist with an EXCLUSIVE lock"* — out-of-process readers are blocked too (reproduced: `second reader under EXCLUSIVE -> database is locked`); ACIS-08/ACIS-11 §11 serve `acis://strategies/provenance` and `acis://params/*` in-process from the same instances, so this matches the spec's design, but any out-of-process harness read of these files must then go through the plane.
  2. **Or detect it exactly:** `PRAGMA journal_mode=WAL` at construction plus `PRAGMA data_version` in the token (`token = (self._db.total_changes, data_version)`) — 12.6 µs per call in WAL here (F-E2), detects other-connection commits exactly (reproduced above), keeps cross-process readers.
  Either way add a regression test that opens a second connection on the store's file, writes a freeze / a promotion through it, and asserts the store either raises (option 1) or returns the new truth on the very next call (option 2).

### F-E2 — The cost claim that justified dropping an exact cross-connection check ("157–163 µs, as much as the 205 µs query it would save") is an artifact of rollback-journal file locking on Windows; the same statements cost 4–16 µs under EXCLUSIVE locking or WAL, and the Linux deploy target was never measured
- Severity: **high** (it is the load-bearing justification in the ledger entry and in the `get_active` docstring) · Likelihood: **high** (reproduced)
- External referents:
  - PRAGMA locking_mode (https://sqlite.org/pragma.html#pragma_locking_mode): *"In NORMAL locking-mode (the default …), a database connection unlocks the database file at the conclusion of each read or write transaction."*
  - File locking (https://sqlite.org/lockingv3.html): before reading *"a process must first acquire a SHARED lock"*; *"Once all reading has completed, the SHARED lock is dropped."* Every autocommit `SELECT` in Python's default mode is therefore one lock/verify/unlock cycle — on Windows a LockFileEx/UnlockFileEx pair plus a header read — which is where the ~150–200 µs goes, not in the query.
- Reproduction (median of 5×20,000 calls, same schema and a JSON payload row, `ext_audit_sqlite.py` and the follow-up script; this machine was quieter than the author's, so the author's numbers are reproduced at the low end):
  ```
  journal=delete locking=NORMAL    keyed SELECT  156.9 us | data_version  144.3 us   (os.stat 135.9 us)
  journal=delete locking=EXCLUSIVE keyed SELECT    5.5 us | data_version    4.0 us
  journal=wal    locking=NORMAL    keyed SELECT   16.0 us | data_version   12.6 us
  journal=wal    locking=EXCLUSIVE keyed SELECT    8.1 us | data_version    3.7 us
  total_changes attribute: 0.5–1.1 us
  ```
  At the author's 2,740 ticks/s the tick budget is ~365 µs; an exact `data_version` check per store per tick costs 2×12.6 µs (WAL, ~7 %) or 2×4 µs (EXCLUSIVE, ~2 %, and then moot because nobody else can write). The ledger's *"a per-call cross-connection check would cost as much as the read it saves"* is true only in the default rollback-journal mode on Windows.
- Consequences: (a) the cross-connection check was not "missed" for lack of a cheap one — a cheap exact one exists (F-E1 fix 2) and a zero-cost enforcement exists (F-E1 fix 1); (b) `KNOWN_GAPS.md` and the `get_active` docstring record "~150–200 µs on the target laptop" without the journal/locking mode that produces it — a future reader on Linux (fcntl locks are far cheaper than Windows file locks) or under WAL will not reproduce it; (c) the cache remains worthwhile for the JSON decode and the per-signal fan-out (six `entry_allowed` calls per tick in AGON), but its exactness no longer needs to be traded away.
- Minimal fix: record the journal/locking mode next to every quoted µs figure in the ledger and docstring; re-measure on the Linux target before the 16-core run; adopt F-E1 fix 1 or 2.

### F-E3 — Ledger closure: the Residual delegates the single-writer requirement to GAP-0091b, which does not own it
- Severity: **medium** · Likelihood: **high** (it is in the diff)
- Referent: CLAUDE.md ledger-closure law — *"Closing needs a residual … `Residual: GAP-… — <what that entry owns>`. A closed label over unowned work is an open wound."* GAP-P12D-15's Residual reads *"GAP-0091b — the production runtime must open each SQLite store once per process (single-writer precondition)"*. GAP-0091b (`KNOWN_GAPS.md` line 415) is *"VaR and cluster/per-instrument metrics need marks fed each evaluate; nothing in production wires the mark stream yet"* — its Description/Justification mention only Risk marks and the account snapshot; the words "SQLite", "store", "connection" or "single writer" do not appear. `scripts/ledger_check.py` passes (150 entries, 0 violations) because the ID resolves, but the requirement is unowned in the sense the law means.
- Also unrecorded: the fact that the engine's fast loop never writes provenance.db (so "until that instance next writes" can be never — F-E1), and that the fold-parallel evolve design (TODO 16-core item) is multi-process by construction and must not share `params.db` / `provenance.db` files across workers with a live engine.
- Minimal fix: either add the single-writer requirement to GAP-0091b's text explicitly, or (better) keep it in GAP-P12D-15 as an open sub-item / a new owned entry, and cite the structural fix chosen under F-E1. Re-run `python scripts/ledger_check.py`.

### F-E4 — Benchmark methodology: the real-tick fingerprint cannot detect a cache that never invalidates, because no lifecycle change happens mid-run in the bench or in the composed-loop test
- Severity: **low** · Likelihood: **high** (by construction)
- Evidence: `bench_replay.py` stages and promotes every regime once *before* the tick loop (`loop.params.promote(BOUNDARY)`), then only calls `loop.on_state`; `PaperLoop.on_state` (tests/integration/paper_loop.py:105–134) never calls `on_boundary`, `demote`, `apply_revalidation` or `stage`. `test_composed_loop_is_identical_with_and_without_the_caches` likewise runs `flat_ticks()` after `make_loop`'s one-time promotion. So for both, `total_changes` never moves during the measured run and a cache with NO invalidation would produce the identical fingerprint. I verified the artifacts the author cites: `base_5k_a/b` vs `new2_5k` and `base_pair_40k`/`new_pair_40k` vs `new2_pair_40k` are identical in `orders` (2,624 / 20,391), `take_rate`, `skips` and `event_counts` — the steady-state claim holds; the invalidation claim rests solely on the two store-level unit tests with synthetic stores (`test_get_active_is_served_from_memory_and_sees_each_promotion_at_once`, `test_entry_allowed_cache_still_freezes_instantly`) and is never exercised through NVMA's `has_params_for=lib.has_active` or AGON's `entry_allowed` in the composed loop. Secondary: the 5k run spans 00:06–02:30 UTC and the 40k run one session; neither completes a rollover-anchored daily bar (22:00 UTC), so the `"/daily"` AtrMemo miss path was exercised only by synthetic bars.
- Minimal fix: one composed-loop test that, mid-stream, (i) stages + promotes at a real boundary with the book flat and (ii) demotes a registered strategy, asserting the next tick's orders/skips change and remain identical with and without the caches; and state in the ledger what the real-tick fingerprint does and does not prove.

### F-E5 — Invariant density (GAP-P12M-02): provenance.py states its single-writer precondition only by cross-reference to another module
- Severity: **low** · Likelihood: **high**
- Evidence: `entry_allowed` carries `# GAP-P12D-15: cached until THIS connection writes (single writer — ParamLibrary.get_active)`; the precondition's mental model (why it holds, what breaks it, the µs claim) lives in `param_library.py`'s `get_active` docstring. `provenance.py`'s module docstring — its one-screen model — does not mention that `entry_allowed` is now a cache with a process-level precondition, although ACIS-11 §7's "instant" freeze is the invariant that cache can break. `test_module_budget.py`: 3 passed; agon.py 506 / capital_governor.py 464 / provenance.py 391 equal their allowlist ceilings (no growth); indicators.py 115 and param_library.py 276 are under 300.

## Honest negatives (claims that survived, with their referent)

1. **`total_changes` is an exact invalidation token for every write path in the two stores — given one connection.** Referents: CPython 3.11 docs — *"Return the total number of database rows that have been modified, inserted, or deleted since the database connection was opened"*; SQLite — *"the total number of rows inserted, modified or deleted by all INSERT, UPDATE or DELETE statements completed since the database connection was opened, including those executed as part of trigger programs … Changes made as part of foreign key actions are included in the count, but those made as part of REPLACE constraint resolution are not. Changes to a view that are intercepted by INSTEAD OF triggers are not counted."* Verified on 3.45.1 (`ext_audit_sqlite.py`): plain INSERT +1; `INSERT … ON CONFLICT DO UPDATE` (what `promote()` uses) +1; `ON CONFLICT DO NOTHING` 0 (no state change either); `INSERT OR REPLACE` +1 (not used by either store; the REPLACE-deleted row is uncounted but the insert is counted); UPDATE to identical values +1; zero-row UPDATE 0 (no state change); `DELETE FROM t` without WHERE +2 (truncate optimisation — https://sqlite.org/lang_delete.html: *"Prior to SQLite version 3.6.5 (2008-11-12), the truncate optimization also meant that the sqlite3_changes() and sqlite3_total_changes() interfaces … will not actually return the number of deleted rows. That problem has been fixed as of version 3.6.5"*; neither store issues a WHERE-less DELETE anyway); `RAISE(ABORT)` trigger 0 (no change); DDL / `executescript(_SCHEMA)` 0 (no row state; CPython: *"If there is a pending transaction, an implicit COMMIT statement is executed first"*); `executescript` DML counted. **Rollback is not decremented** (rolled-back transaction: delta +1 with 0 rows in the table) — the direction is safe: a rollback over-invalidates, never under-invalidates. Net: with one connection, token unchanged ⟹ row state unchanged.
2. **Frozen dataclass + identity as the memo key is exact given the codebase's own discipline.** Referents: dataclasses docs — *"It is not possible to create truly immutable Python objects. However, by passing frozen=True … you can emulate immutability … will raise a FrozenInstanceError"*; `id()` docs — *"unique and constant for this object during its lifetime. Two objects with non-overlapping lifetimes may have the same id() value."* The memo stores `tuple(bars)`, so every compared object's lifetime overlaps the cache entry's — id reuse is structurally impossible; `all(map(operator.is_, hit[0], bars))` after the length check is a full positional identity test. `grep object.__setattr__` over the repo: no uses; `Bar` fields are `datetime`/`float`/`int` (immutable). `wilder_atr` → `atr_series` reads only `high/low/close` and `period` (pure). AGON's five signal-bar callers and `_pair_divergence` share key = instrument AND the same window `self._bars[instrument]`, so the shared key does not thrash; TSMOM uses a separate `"/daily"` key; the Governor has its own memo over the same Bar objects AGON produced (GAP-0059).
3. **The author's "tests only reopen a store after closing it" is true.** Both double-open sites close first: tests/integration/test_qiea_promotion_cycle.py:72–73 (`lib.close()` then `lib2 = ParamLibrary(db, …)`), tests/unit/test_provenance.py:177–178 (`store.close()` then `store2 = ProvenanceStore(…)`). No production constructor of either store exists outside tests/integration/paper_loop.py (`grep ParamLibrary\(|ProvenanceStore\(` outside tests: none).
4. **The author's µs figures reproduce in the mode they were taken in.** Default rollback-journal, NORMAL locking: keyed SELECT 157–208 µs, `PRAGMA data_version` 144–202 µs, `os.stat` 96–136 µs on this laptop (author: 157–205 µs). The disagreement is in the conclusion, not the measurement (F-E2).
5. **Restart is covered for both stores.** Caches start empty in both constructors; `test_get_active_reads_fresh_after_a_restart` (new) and `test_restart_resumes_rungs_freezes_and_counters` (existing, exercises `entry_allowed` on a reopened store) reload from disk.
6. **Exception mid-fill cannot leave a half-filled cache that is later trusted.** `ProvenanceStore`: `self._gates` is assigned only after the full comprehension, `self._gate_token` after that; a raise leaves both old and the next call retries. `ParamLibrary`: the dict is replaced empty before per-regime fills, and a failing `_read_active` leaves that regime absent so the next call re-reads. Neither cache is consulted inside a `with self._db:` block.
7. **Counter width is a non-issue in practice.** CPython 3.11 `Modules/_sqlite/connection.c`: `return Py_BuildValue("i", sqlite3_total_changes(self->db));` — the 32-bit variant; SQLite: *"if the number of rows modified by the connection exceeds the maximum value supported by type 'int', then the return value … is undefined."* 2^31 row changes on one engine connection (writes happen per boundary / per verdict / per attempt) is unreachable in any realistic process lifetime; noted so a future reader does not rediscover it. (`sqlite3_total_changes64` exists since 3.37 but CPython does not expose it.)
8. **Thread premise.** CPython default `check_same_thread=True`: *"ProgrammingError will be raised if the database connection is used by a thread other than the one that created it."* Master §10's three asyncio loops share one thread, so "own connection" also means "own thread" — a second thread cannot silently write through these connections.
9. **`PRAGMA data_version` is the documented exact detector and behaves as documented here** (https://sqlite.org/pragma.html#pragma_data_version: *"different if changes were committed to the database by any other connection in the interim … unchanged for commits made on the same database connection … the same for all database connections, including database connections in separate processes"*) — reproduced: changed after the other connection's commit, unchanged after own writes.
10. **Module budget and ledger check are green** (`tests/unit/test_module_budget.py`: 3 passed; `scripts/ledger_check.py`: 150 entries, 0 violations) — subject to F-E3's point that a resolving ID is not the same as an owning entry.
11. **WAL caveats, if F-E1 fix 2 is chosen** (https://sqlite.org/wal.html): *"All processes using a database must be on the same host computer; WAL does not work over a network filesystem"*; adds `-wal`/`-shm` files next to `params.db`/`provenance.db` (relevant to the systemd `ReadWritePaths` hardening in deploy/README.md).
