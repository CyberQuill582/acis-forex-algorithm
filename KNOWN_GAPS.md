## GAP-0051: The single-currency net-delta cap has no risk-direction awareness — when existing exposure already exceeds the cap, a risk-REDUCING order that still leaves it over the cap is blocked (`currency_delta_cap`); the Governor's stated "can only ever reduce risk" is contradicted for de-risking orders

- Likelihood: low (standalone) — but composes with GAP-0049, which makes over-cap states reachable
- Status: closed (fixed 2026-07-16 by the author, superior-tier review — the delta cap now blocks only orders that INCREASE |delta| beyond the cap (`abs(new) > cap AND abs(new) > abs(old)`); an order reducing an existing breach always passes, honouring §1 'can only ever reduce risk'. - Description: the delta hard limit is `if abs(new_delta) > delta_cap: zero`, where `new_delta = existing + contribution`. ## GAP-0050: `apply_risk_state` lets the risk-restrictive upward edge RAISE a size — a partial-parameter call (e.g. `apply_risk_state(taper_factor=0.9)`) silently clears an active `alpha_decay` throttle via the `alpha_decay=False` default, ~3.6×-ing the next size; the GAP-0014 "the upward edge can never raise a size" invariant is falsified

- Likelihood: medium
- Status: closed (fixed 2026-07-16 by the author, superior-tier review — `apply_risk_state` parameters are now None-sentinels: None means UNCHANGED, so a taper-only call can never implicitly clear an active alpha-decay throttle (the auditor's 3.6× exploit); clearing decay requires an explicit `alpha_decay=False` and logs `ALPHA_DECAY_CLEARED` (audited relaxation — legitimacy conditions are ACIS-07's phase-9 contract). - Area: [DIR:core/governor] capital_governor.py `apply_risk_state`, ACIS-05 §6.3/§12/§13 C-GOV-9, SPEC §9.5/GAP-0014
- Description: ACIS-05 §6.3 and §12 state the single upward edge "rejects any taper > 1.0, any alpha-decay multiplier > 1.0, and any instruction that would raise a size — `DataQualityError`, logged." `apply_risk_state(*, taper_factor=1.0, alpha_decay=False)` enforces only the first two: it validates `0.0 <= taper_factor <= 1.0` and then unconditionally assigns `self._taper_factor` and `self._alpha_decay = alpha_decay`. Add §14 tests for (a) taper-only update preserves an active decay, (b) a taper increase from a lower prior value is rejected or explicitly justified. Guardrail-adjacent (the GAP-0014 risk-restrictive-only upward-edge invariant) — also summarised in SPEC_AUDIT.md. High severity (a stated hard invariant of the sole upward risk edge is violated), medium likelihood (per-cycle partial state updates from Risk are ordinary). Finder-only.

## GAP-0013: §7.5 shared platform-session object is an unpoliced upward channel (layer-law bypass)
- Severity: high
- Likelihood: medium
- Status: closed (resolved in SPEC v2.5 §7.5 — shared session object is transport/auth only, carries no market/account/position state; feed face exposes no account surface, asserted structurally by the conformance suite)
- Area: [DIR:core/data]/[DIR:core/execution], SPEC §7.5 vs §2, audit F28/C13
- Description: §7.5 splits each adapter into a feed face in `core/data/feeds.py` (layer 1) and an execution face in `core/execution/venue.py` (layer 6), and explicitly permits: "The two faces **may share a platform session object owned by the adapter package**." Its only stated safeguard is "neither face ever imports a core layer above its own" — an *import-direction* guarantee, enforced by the §2 import-linter contract test. But a shared mutable session object is a runtime data channel that **no import crosses**: the execution face (layer 6) fetches and caches account state (positions, equity, fills) on the shared object; if any feed-face code (layer 1) reads that state off the same object — e.g. to filter instrument discovery by tradeable balance, or because the session exposes `session.positions`/`session.equity` — then account/execution state has flowed from layer 6 up to layer 1, a 6→1 upward data flow that §2 forbids ("communication flows downward only … exactly one exception: the Risk Monitor's upward HALT channel"). The import-linter cannot catch it because neither face imports the other; the violation lives in the shared object the adapter package owns, which both faces legitimately import. Failing scenario: an adapter caches `account.free_margin` on its session for the execution face; a well-meaning feed-face optimization skips quoting instruments the account can't afford by reading `session.free_margin` — instantly a layer-6 account fact steering layer-1 data production, upward, invisibly to the guard. The guard-integrity spirit (§9: "a guardrail a guarded process can reach is not a guard") applies to the layer law too: a law enforced only by an import-linter, with a spec-sanctioned shared-object side channel the linter cannot see, is reachable.
- Justification: ACIS-13 must forbid the shared session object from carrying any state upward — either the two faces share only a transport/auth handle (no account or position state readable by the feed face), or the shared object is split so the feed face physically cannot reach execution/account fields, plus a runtime/contract test that asserts the feed face never reads account state (not just that it doesn't import upward). Architectural — human/deep-spec owned.
- Linked: SPEC_AUDIT.md F28, ACIS_SPEC.md §7.5/§2, specs/ACIS-13-VENUE_ADAPTERS.md
